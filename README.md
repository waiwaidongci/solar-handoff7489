# 光伏逆变器晨检分区交班

云岬光伏站巡检班，3 个逆变器分区各有 3 台设备，运行值班长复核晨班交接。。站控值班员汇合签核计划、设备台账和采集网关心跳后提交晨检，运行值班长复核，东区、西区、南区的检修接班组各自查收所属分区报告。

输入一份晨检 CSV，每行标注上海晨检日期和区域。plan 行签核本班应检台数，roster 逐台列应检设备，calibration 按批次补录网关校时版本和允许的整数秒误差区间（含端点），heartbeat 记录设备、心跳时间及其校时批次。未用的设备编号和心跳时间填 -，非 plan 行的应检台数填 0。心跳使用 ISO 8601，未写偏移时按上海时间解析。同批心跳共用一个偏移，各批可不同；旧版六列表头仍可兼容，按 B1 批次、版本 1、误差 0 秒处理。 每次计算提交一个分区一个晨班的交班报告，附逐台最新心跳、归属分钟、校时依据和全偏移组合门槛结论。批准后为该区值班组安排单次站内投递，明细可下载为 CSV。

- 网关同分钟重发会在手工表里抬高已收记录数。
- 只有上报设备的 CSV 会掩盖完全缺心跳的逆变器。
- 沿用上一班已齐备的报告会掩盖当日某分区的延迟。
- 网关时钟跑偏后，只看单一时间点会放过在允许误差边缘过期的设备，因此按全部允许偏移组合做门槛。
- 校时记录乱序到达或并发重算时，旧版本只保留审计，不能恢复待发报告的投递资格。

## 六个业务模块

1. 晨检交班总览
2. 逆变器与心跳台账
3. 晨班窗口与校时配置
4. 分区心跳与校时明细
5. 全偏移组合门槛复核
6. 接班组报告投递

## 工作剧本

1. 2026-11-24 06:00（上海），运行值班长确认东区、西区、南区各 3 台应检逆变器。
2. 07:05 分析员导入 云岬光伏站晨检-20261124.csv，包含 11 月 23 日和 24 日两班计划、名册及心跳。
3. 07:06 以 07:00 为截点、15 分钟为上限，分别运行 11 月 24 日东区、西区和南区报告。
4. 07:07 在东区明细核对 E-02 的 06:56:12 和 06:56:54 归并成一条，E-01 的 07:00:00 不进入晨检窗口。
5. 07:08 复核员批准东区 3 台均新鲜且全偏移组合稳健的报告，退回 W-03 在 B2 批次存在失鲜偏移的西区报告，以及名册只有 2/3 台且 S-02 缺心跳的南区报告。
6. 07:10 将已批准报告导出 CSV，为东区检修接班组设置上海时间 07:15 单次投递。回放样例时改用未来的整分钟投递。
7. 07:12 上游补推 B1 校时版本 2：引用版本 1 的待发报告立即失效、计划停用，复核员重新运行分析并复核后再投递；已入箱报告保留版本 1 依据。
8. 07:15 东区检修接班组在收件箱查阅报告，西区与南区补核原始晨检证据后再为各自报告申请投递。

## 算法与复核

默认取整份 CSV 的最新晨检日期，也可指定日期。以 Asia/Shanghai 06:00 为含起点，截点为不含终点。同区同设备同本地分钟只保留最晚的心跳。修正时间为心跳时间加所属批次偏移；截点与最后归属分钟相差不超过新鲜度上限即为新鲜，默认 15 分钟。签核台数须与去重名册相等，且每台应检设备在所有允许的批次偏移组合下都须有新鲜心跳，才满足交班门槛；未通过时明细逐台给出会失败的一组偏移见证、失败组合数和受影响设备。

缺应检计划、去重名册台数和签核台数不符、应检设备缺心跳，或心跳在任一允许偏移组合下过期时，工作稿保留原因并拦截审批和定时派发。错填班次、非法时间、同版本冲突的误差区间或心跳引用未登记批次须修正 CSV 后重跑。校时记录只追加，同批次取最大版本为当前依据；乱序到达的旧版本保留审计但不会成为当前版本。 复核问题为「本区本班的应检名册是否齐全，逐台心跳是否足够新鲜，可以交给本区检修接班组吗？」。每次分析绑定数据版本、参数和校时依据版本，原始数据按规范化内容的 SHA-256 去重。上游校时版本更新后，引用旧依据的待发报告立即失效（`calibration_stale` 只做 0→1），投递计划同步停用，重新运行分析并复核产生新任务后才能投递；已送达报告在收件箱保留当时校时版本。日程针对已复核的固定结果版本，每日模式按初次投递时间每 24 小时重复。停机期间错过多次时只补一份到站内收件箱，下一次回到原时间点。

| 字段 | 含义 | 类型 |
|---|---|---|
| `shift_date` | 上海晨检日期 | str |
| `zone` | 逆变器区域 | str |
| `kind` | 记录类型（plan/roster/calibration/heartbeat） | str |
| `inverter_id` | 逆变器编号 | str |
| `heartbeat_at` | 心跳时间 | str |
| `expected_count` | 计划应检台数 | int |
| `batch_id` | 校时批次（同批共用偏移） | str |
| `calibration_version` | 校时版本（从 1 递增） | int |
| `offset_lower_seconds` | 允许偏移下限（整数秒，含端点） | int |
| `offset_upper_seconds` | 允许偏移上限（整数秒，含端点） | int |

## 启动

```sh
[ -f .env ] || cp .env.example .env
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

- Web 界面 `http://127.0.0.1:18301`
- API 文档 `http://127.0.0.1:19301/docs`
- 数据库端口 `17801`
- 后端纯逻辑测试（仅标准库，无需数据库）：`cd backend && python3 -m unittest discover -s tests`

| 账号 | 演示密码 | 工作权限 |
|---|---|---|
| analyst | analyst-demo-24 | 导入 CSV、运行分析、导出工作稿 |
| reviewer | reviewer-demo-24 | 复核、设置和停止投递、导出 |
| viewer | viewer-demo-24 | 浏览结果、导出已批准的报告、查收投递 |

原生 HTML/CSS/JavaScript 前端与 Nginx、FastAPI、Python worker、MySQL 8.0 和 Redis 组成五服务 Compose。`backend/src/services/domain.py` 存放业务算法，`domain.json` 定义字段与验收口径，`frontend/src/pages` 为业务页面。更新任一侧源文件后，用 `docker compose up -d --build` 重建对应镜像。`backend/src/constants/enums.py` 和 `frontend/src/constants/enums.js` 定义角色及运行状态。`.env` 支持前端、API、数据库端口、演示 seed 开关和 JWT 密钥。首次部署到非演示环境时更换演示身份及 JWT/数据库凭据。

`docker compose down` 停止服务并保留数据卷。现场数据和演示结果可以在各自版本中并存。
